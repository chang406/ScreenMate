## 1. 타임라인: 피드백 → 원인 → 수정

### PR #1 이후: 첫 Windows 실행
- **결과**: 사용자가 PR 브랜치를 받아 실행, 대략적인 동작에 이상 없음을 확인.
- **CI 보강**: "Windows는 테스트 못 하나?"라는 질문 → `windows-latest`에서 빌드·테스트·`.exe` 15초 실행 확인 작업 추가. 첫 실행부터 통과.

### 피드백 ① "노트북에서는 캐릭터가 화면 밖으로 넘어가 드래그도 크기 조절도 안 된다" → PR #2
| 조사로 찾은 원인 | 수정 |
| :--- | :--- |
| 640×920 고정 창이 노트북 작업 영역보다 큼 (예: 1366×768@125% → 쓸 수 있는 높이 708px, 창은 1150px) | 창 크기를 모니터 작업 영역에 맞춤 (`window_fit.rs`) |
| **(작업 중 새로 발견)** 배율 125%/150%에서 Live2D 위치를 버퍼 픽셀(`canvas.width`) 기준으로 계산해 캐릭터가 **창 아래 밖에 그려짐** | Pixi 스테이지 크기(CSS 픽셀) 기준으로 계산. `--dpr` 스모크로 전후 스크린샷 확보 |

> 💡 두 번째 원인은 사용자가 말한 증상("노트북에서 안 됨")을 재현하려고 배율 150%로 렌더링해 보다가 발견했습니다. **증상 설명이 없었다면 자율 단계에서는 찾지 못했을 결함**입니다.

### 피드백 ② "클릭 범위가 눈에 안 보이고, 팔 1픽셀 옆은 안 눌린다" → PR #3
- **원인**: "캐릭터 위" 판정이 실제 모양이 아니라 **사각형**이었음 (Live2D는 고정 비율 사각형, 2D는 이미지 전체).
- **수정**: 그려진 픽셀(+6px 여유) 기준 판정, "🎯 클릭 영역 보기" 추가. 사용자 질문("새로 추가하는 캐릭터에도 되나?")에 맞춰 **캐릭터별 설정 없이** 동작하는 방식으로 설계.

### 피드백 ③ "우클릭 메뉴 아래가 가끔 잘린다" → PR #3 추가 커밋
- **원인**: 메뉴 열림 애니메이션(92%→100%) 도중 크기를 재서 8% 작게 계산됨. 메뉴 항목이 늘며 드러남.
- **수정**: 애니메이션 영향 없는 크기로 측정 + 낮은 창에서는 스크롤. CI에 "메뉴가 창 안에 있는지" 검사 추가.

### 피드백 ④~⑦ 위치 규칙 — **같은 문제에 대한 4번의 반복**
| 차수 | 사용자 피드백 | AI 판단·수정 | 결과 |
| :--- | :--- | :--- | :--- |
| 1차 | 캐릭터를 위로 올리면 특정 높이 아래로 내려옴 | "창 전체가 화면 안" 규칙이 너무 엄격 → "캐릭터 자체가 화면 안"으로 완화 | ❌ 여전히 조금씩 되돌아감 |
| 2차 | 아직 안 됨. **"y축 위치 제한이 필요한가?"** | 드래그 후에는 1/3 이상 보이면 그대로 두기 | (테스트 전 방향 전환) |
| 3차 | **얼굴만 빼꼼, 화면 밖으로 숨기기도 의도한 사용법.** 자동 복구 대신 메뉴로 불러오게 해 달라 | 드래그 위치는 절대 안 바꿈 + "화면 가운데로 불러오기" 추가 | 아래로는 됨, **좌우 절반·위로는 여전히 안 됨** |
| 4차 | (위와 같음) | 원인이 앱 규칙이 아니라 **Windows 기본 창 이동이 창 꼭대기를 화면 위로 못 가게 막는 것**임을 파악 → 드래그를 앱이 직접 처리 | ✅ 상하좌우 모두 숨기기 가능 |
| + | 앱을 새로 켜면 그냥 정중앙에서 시작 | 위치 기억 기능 제거, 항상 주 모니터 중앙 시작 | ✅ |

> 💡 **교훈**: 1~3차에서 AI는 "보이는 증상"을 기준으로 규칙만 계속 조정했고, 진짜 원인(OS 제한)은 4차에야 찾았습니다.
> 사용자의 **의도**("숨기는 것도 사용법이다")가 나오기 전까지는 "화면 밖으로 나가지 않게 막는 것"이 맞다고 판단하고 있었습니다.

## 2. 실험 결론: 자율 단계 vs 피드백 단계

| | 자율 단계 (PR #1) | 피드백 단계 (PR #2~#5) |
| :--- | :--- | :--- |
| 잘 된 것 | 테스트로 드러낼 수 있는 결함(로그 분류, 이벤트 유실, 탐색 비용), 로드맵 항목 구현, 기록·CI 체계 | 실제 사용에서만 보이는 문제(노트북 배율, OS 창 이동 제한, 메뉴 측정 타이밍), 사용 의도 반영 |
| 한계 | Windows 실기기·실제 사용 감각을 확인할 수 없음. "검증 못 함"으로 남긴 항목이 실제로 문제였음 | 증상만 보고 규칙을 조정하면 같은 문제를 여러 번 반복함 (위치 규칙 4회) |
| 사람의 역할 | 최초 요청 + 기록 요청 | **사용 의도 설명**, 실기기 테스트, 스크린샷 제공, 방향 결정 |

**한 줄 요약**: AI는 **검증 가능한 품질**(테스트·정적 분석·성능·문서)은 혼자 꽤 멀리 끌고 갔지만, **"어떻게 쓰고 싶은가"**와 **실기기에서만 보이는 문제**는 사람의 피드백이 있어야 맞춰졌습니다. 그리고 피드백 단계에서도 **증상보다 의도를 먼저 물었다면** 반복이 줄었을 것입니다.
